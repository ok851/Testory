## 移动端 APK 连 PC 失败（根因已定位并修复）
- 现象：APK 输入 192.168.2.38:5000 + 六位配对码 → "无法连接"（`SettingsViewModel.kt` 通用提示）。之前能连、重组后不能。
- **根因（决定性证据来自 `AppData/Local/Testory/logs/backend_startup.log`）**：
  - werkzeug 3.0.1 开发服务器的请求读取 `werkzeug/serving.py:347 self.rfile.read(10_000_000)` —— 每个请求要**一次性分配 10MB 缓冲**。
  - Flask 后端长期运行（Tauri 桌面模式 `FLASK_DEBUG=None`、生产式常驻）后内存紧张，该 10MB 分配抛 **`MemoryError`**，且崩溃发生在 **URL 解析之前**（werkzeug `run_wsgi`→`execute` 阶段），所以请求根本不会被记成一条 URL 日志，只留下 `Error on request: MemoryError`。
  - 后果：手机 `ping`/`pair/confirm` 请求在 socket 读取阶段被静默打挂 → APK 拿到非 200/连接错误 → 报"无法连接"。日志里"手机没发请求"正是这个假象。
  - 时间线印证：27/Aug 15:57 连续 `MemoryError`；当日 17:03:59 用户重启（进程全新、内存干净）→ 17:04:10 `pair/init` 成功生成码，但手机 `pair/confirm` 始终未出现在日志（撞上崩溃被吞）；排查时活服务器已无 5000 监听（OOM 崩溃退出）。
  - 与"导入丢失/协议/子网"无关——curl 端到端实测 ping/pair/init/pair/confirm 均 200；IP 固定、网络不变（25/Aug 真机 192.168.2.4 曾成功连过）。
- **修复**（`app.py` `__main__` 启动逻辑改造）：
  - 弃用 werkzeug 开发服务器；改用**生产级/稳定 WSGI 服务器**，三级容错：
    1. `waitress`（生产级，内存稳定、抗并发）—— 沙箱无网装不上，主机有网可后续 `pip install waitress` 自动启用
    2. `wsgiref(ThreadingWSGIServer)`（**标准库自带、零安装**，逐行读请求、不一次性分配 10MB）→ 当前生效路径
    3. werkzeug 开发服务器（仅兜底）
  - 新增 `_AccessLogMiddleware`：**请求一到达就记录** `method+path+remote_addr`（不等待处理结果），确保今后任何连接问题都能在日志看到手机到底有没有把请求发过来（正是本次缺的关键可观测性）。日志写 stdout，由 Tauri 捕获进 `backend_startup.log`。
