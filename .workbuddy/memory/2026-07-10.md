## Tauri 模式 auth 页面背景被浅色覆盖修复

### 用户二次反馈
登录/注册/找回密码页背景仍然是浅色（与启动页深色不一致）。前面修改后浏览器渲染**仍然显示** `rgb(226, 232, 240)` = `#e2e8f0`（浅色），不是预期的 `#050816`（深色）。

### 真正的根因（特异度问题）
- `body.testory-desktop-client`（特异度 0,1,1 = 1个类型选择器 + 1个class）`background: #e2e8f0` 覆盖了
- `.testory-auth-page`（特异度 0,1,0 = 仅1个class）`background: var(--testory-bg-deep)`
- 两者顺序上 `.testory-auth-page` 在后，但 `body.testory-desktop-client` 的**类型选择器多 1 个权重**（0,1,1 > 0,1,0）
- 所以前者在所有情况下都胜出，无论源码顺序

### 修复
在 `testory-brand.css` L70 后插入更高特异度的规则：
```css
body.testory-desktop-client.testory-auth-page {
  background: var(--testory-bg-deep);  /* 特异度 0,2,1 */
}
html.dark body.testory-desktop-client.testory-auth-page {
  background: var(--testory-bg-deep);
}
```
同时把 `.testory-auth-page::before` 渐变改为与 `tauri_splash.html` 启动页**完全一致**的：
```css
radial-gradient(circle at 20% 20%, rgba(99,102,241,0.25), transparent 45%),
radial-gradient(circle at 80% 0%, rgba(6,182,212,0.18), transparent 40%),
var(--testory-bg-deep)
```
CSS 版本号 webui6→7, v=3→4。

### 调试经验
- Flask app.py 硬编码 5000 端口，传 `--host/--port` 无效
- 走 Tauri 渲染分支必须用 `TESTORY_TAURI_MODE=1` 启动 Flask
- 验证：Playwright 启动后 `getComputedStyle(body).backgroundColor` 应该是 `rgb(5, 8, 22)`

## 移动端连接 Gateway 鉴权失败诊断

### 用户报错
截图显示：连接失败: Gateway 鉴权失败 — Flask 用的 secret=hufirs... 与 Gateway 不匹配。 请重启后端服务 (python app.py) 以同步环境变量

### 根因分析（三个进程/路径，secret 来源可能不一致）
1. **Flask 进程（app.py）**：`mobile_routes._gateway_diagnostics()` → `mobile_agent_config()`
   - `mobile_agent_client.py:38-55` 优先级：env `MOBILE_AGENT_GATEWAY_SECRET` > .env 读 > env `EMBEDDED_BROWSER_GATEWAY_SECRET` > .env 读 > 默认 `hufirst-mobile-local`
   - 关键：**会** `load_dotenv(env_path, override=True)` 重新覆盖 `os.environ`
2. **Flask 启动的 Gateway 子进程**：`mobile_service_bootstrap._start_gateway_process()`
   - 优先级：env `MOBILE_AGENT_GATEWAY_SECRET` > env `EMBEDDED_BROWSER_GATEWAY_SECRET` > 默认 `hufirst-mobile-local`
   - 关键：**不**读 .env 文件，只用当前 `os.environ`（依赖 `app.py` 启动时 load_dotenv 后传入）
3. **外部独立启动的 Gateway 进程**（TestoryMobileGw.exe / 独立 python）：用进程**自己启动时**的环境变量，不会再读 .env

### 当前 .env 配置（问题源头）
- `EMBEDDED_BROWSER_GATEWAY_SECRET=replace-with-same-secret-as-gateway` ← **占位符未替换**
- `MOBILE_AGENT_GATEWAY_SECRET=hufirst-mobile-local` ← 默认值

### 三种典型失败场景
1. **外部 Gateway 进程在 8777 端口运行**（常见：用户之前手动启过、或者 testory-desktop.exe 启的内置 Gateway 与 Flask 进程不一致）
   - 验证：`netstat -ano | grep :8777` → 看是不是 flask 进程（同一 pid 树）
   - 当前实际：8777 端口被独立 python 进程（PID 19452）占用，**不是 flask 启动的子进程**
2. **`.env` 中 `EMBEDDED_BROWSER_GATEWAY_SECRET=replace-with-same-secret-as-gateway`**（占位符没改）
   - 如果 Gateway 端用 `EMBEDDED_BROWSER_GATEWAY_SECRET` 而 Flask 端 fallback 到 `MOBILE_AGENT_GATEWAY_SECRET`，两个值不同
3. **app.py 启动时 load_dotenv 失败 / 找错 .env**
   - 走 fallback `hufirst-mobile-local`（前6字符 = hufirs...）

### 用户验证 / 解决
- 让用户改 `.env`：把 `EMBEDDED_BROWSER_GATEWAY_SECRET=replace-with-same-secret-as-gateway` 改为实际值（与 `MOBILE_AGENT_GATEWAY_SECRET=hufirst-mobile-local` 一致，或换成自定义密钥）
- 杀掉端口 8777 旧进程：`netstat -ano | findstr :8777` 找到 PID → `taskkill /F /PID <pid>`，然后重启 `python app.py`

### 代码修复（Tauri 模式 secret 不一致根因）
**根因**：Tauri 的 `flask_process.rs` 设置了 `EMBEDDED_BROWSER_GATEWAY_SECRET=hufirst-desktop-local` 但**没设** `MOBILE_AGENT_GATEWAY_SECRET`。Flask 启动时 `_ensure_mobile_env_defaults()` 用 `EMBEDDED_BROWSER_GATEWAY_SECRET` 作为 fallback 给 Gateway → Gateway 拿到 `hufirst-desktop-local`。但 `mobile_agent_config()` 后续调用 `load_dotenv(override=True)` 从项目根 `.env` 读取 `MOBILE_AGENT_GATEWAY_SECRET=hufirst-mobile-local` **覆盖**了 `os.environ`，导致 Flask 路由用 `hufirst-mobile-local`，与 Gateway 的 `hufirst-desktop-local` 不匹配。

**修复两处**：
1. `src-tauri/src/flask_process.rs`：在 `EMBEDDED_BROWSER_GATEWAY_SECRET` 旁边新增 `.env("MOBILE_AGENT_GATEWAY_SECRET", "hufirst-desktop-local")`，Tauri 显式设置两个 secret 一致
2. `mobile_agent_client.py`：`mobile_agent_config()` 中 `load_dotenv` 从 `override=True` 改为 `override=False`，防止 `.env` 覆盖 Tauri/父进程已设置的环境变量

**修复后 secret 传递链**（Tauri 模式）：
- Tauri → Flask env: `MOBILE_AGENT_GATEWAY_SECRET=hufirst-desktop-local`
- app.py `load_dotenv(override=False)` → 不覆盖 → `os.environ` 仍为 `hufirst-desktop-local`
- `_start_gateway_process()` → Gateway 子进程拿到 `hufirst-desktop-local`
- `mobile_agent_config()` → `load_dotenv(override=False)` → 不覆盖 → 返回 `hufirst-desktop-local`
- 两端一致 ✓

**Web 模式**（`python app.py` 直接启动）不受影响：
- 无 Tauri env → app.py `load_dotenv(override=False)` 从 .env 加载 `hufirst-mobile-local`
- Gateway 和 Flask 路由都拿到 `hufirst-mobile-local` → 一致 ✓

### 用户手动关闭浏览器窗口的处理流程
1. 用户关闭浏览器 → Playwright `disconnected` 事件 → `_handle_browser_disconnect_sync()` 设置 `automation.browser = None`
2. 下一个 Web 步骤 → `_ensure_browser_for_web_step()` 检测 `automation.browser is None` → 抛出"浏览器已关闭"异常
3. 异常被外层处理器捕获 → 匹配"浏览器已关闭" → 归类为 `stopped` 而非 `error`
4. finally 块释放锁 → 用户可立即再次运行

## 运行/停止状态管理重写 + 进度条持久化

### 用户反馈
1. 进度条悬浮窗不是持久化显示，运行中有时不显示
2. 运行/停止/再运行流程仍不理想，代码冗余

### 根因
1. **双状态标志冗余**：`localCaseExecutionRunning`（本地布尔）和 `__uatCaseRunInFlight`（全局槽位）两个标志管理同一状态，容易不同步
2. **runTestCase 先获取槽位再检查本地标志**：如果 `uatTryAcquireCaseRunSlot()` 返回 true 但 `localCaseExecutionRunning` 为 true，函数返回但**不释放槽位** → 永久死锁
3. **stopCaseRun 过早释放槽位**：停止后立即释放 `__uatCaseRunInFlight`，用户可点击新运行，但后端锁仍持有 → 409 lock:busy 错误
4. **_pollGlobalRunBanner 不考虑前端运行状态**：首次轮询时后端可能尚未设 active → banner 被隐藏
5. **_stopGlobalRunTask 立即隐藏 banner**：停止时无视觉反馈
6. **_kickRunBanner 有 500ms 延迟**：banner 显示不及时

### 修改

**list_cases_v2.html**：
- 删除 `localCaseExecutionRunning`，统一用 `_isRunBusy()` 检查 `window.__uatCaseRunInFlight`
- `runTestCase()` / `executeSelectedCases()`：先检查 `_isRunBusy()` 再获取槽位；finally 块释放槽位 + 清除 `__uatCaseRunStopping` + kick 轮询
- `stopCaseRun()`：只发送停止信号，**不释放槽位**；设置 `__uatCaseRunStopping=true`；15 秒安全超时强制释放
- `syncCaseRunButtonState()`：控制停止按钮文案（"停止运行"/"停止中..."）、禁用所有运行按钮、非忙碌时轮询后端跨标签页同步
- `_kickRunBanner()`：去掉 500ms 延迟，立即 kick
- `loadTestCases()` 末尾调用 `syncCaseRunButtonState()` 确保新渲染按钮状态正确

**base.html**：
- `_pollGlobalRunBanner()`：新增 `localInFlight` 检查 — `__uatCaseRunInFlight` 为 true 时即使后端未设 active 也保持 banner；显示"正在停止..."/"执行中..."
- `_stopGlobalRunTask()`：不立即隐藏 banner，设 `__uatCaseRunStopping=true` + 显示"正在停止..." + kick 轮询
- `_globalRunPollTick()`：活跃时轮询间隔 2s→1.5s，空闲 15s→12s
- 新增翻译键：`tc_banner_stopping`、`tc_stopping`（zh/en）

**list_steps.html**：
- `stopRunCase()`：添加 `window.__uatCaseRunStopping = true`
- `runTestCase()` finally 块：清除 `window.__uatCaseRunStopping = false`

### 状态管理架构（修复后）
- **单一前端状态源**：`window.__uatCaseRunInFlight`（全局槽位）
- **生命周期**：runTestCase/executeSelectedCases 获取 → finally 释放；stopCaseRun 不触碰
- **停止流程**：stopCaseRun 发送信号 → 后端 Event → 执行线程检测 → fetch 返回 → finally 释放
- **安全网**：15 秒超时强制释放 + 后端 10 秒锁超时
