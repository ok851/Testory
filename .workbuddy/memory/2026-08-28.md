## 「关闭软件导致进程卡死」排查与修复

用户报：关闭 Testory 软件时进程卡死、无法像以前那样正常关闭。

### 根因（实证）
- 启动链：Testory.exe → testory_exe_launcher.py → uat_desktop.py（父壳）subprocess.Popen 起后端 app.py → app.py 内部 `_boot_desktop_side_services`/`_boot_mobile_side_services` 线程里 spawn 桌面/移动网关；Hermes 网关由 UI 触发后在 app.py 进程内 spawn。这些都是 **backend 的孙进程**。
- 关闭时 `_shutdown_all(proc)` 在父壳执行：`proc.terminate()`（Windows 即 TerminateProcess，**不递归杀子进程**）→ 后端 app.py 被杀死，但它在进程内 spawn 的 Hermes(8642)/桌面(8766)/移动(8777) 网关变成**孤儿进程**继续存活 → 端口被占、进程管理器里残留、下次启动冲突。父进程 `stop_hermes_gateway`/`stop_desktop_gateway`/`stop_mobile_gateway` 的模块级 `_GATEWAY_PROC` 在父进程中永远是 None（spawn 发生在 app.py 内），根本杀不到这些孙进程。
- 实证：关闭后 `netstat` 显示 5000（后端）已下线，但 8642/8766 仍在 LISTENING（PID 孤儿）。已用 Stop-Process 清理。

### 已修复
- `packaging/uat_desktop.py`：新增 `_kill_process_tree(pid)`（Windows `taskkill /T /F /PID`，其他平台 `os.killpg(SIGKILL)`），在 `_shutdown_all` 中**先递归杀 backend 进程树**（连同 Hermes/桌面/移动网关孙进程），再兜底调用 `shutdown_all_services()` 做端口回收。编译通过。
- 注意：改动在 `packaging/uat_desktop.py`（桌面启动器源码）。若已发布为打包 exe（`dist/uat_release/...`），需重新打包或确保运行时用的是源码布局。

## 「agent 一收到命令就执行失败: HTTP 500」真正根因（三次排查，推翻前两次结论）

用户指出模型额度未耗尽、且以前额度耗尽时报 403 而非 500 —— 用户是对的，前两次结论有误。

### 真正根因（铁证：backend_startup.log 末尾 traceback）
```
File "...python-3.12\Lib\wsgiref\handlers.py", line 246, in start_response
    assert not is_hop_by_hop(name)
AssertionError: Hop-by-hop header, 'Connection: keep-alive', not allowed
```
- **这是我 8/27 修 APK 连接问题时把常驻服务器换成 wsgiref 引入的回归**。
- app.py 有 4 处 SSE 路由显式设置 `'Connection': 'keep-alive'`（L7997、L8156、L9599、L18753，含 `/api/ai/task/execute`）。werkzeug 静默容忍 hop-by-hop 头；wsgiref/waitress 严格执行 WSGI 规范（PEP 3333 禁止应用下发 Connection/Keep-Alive/Transfer-Encoding/Upgrade/TE/Trailers/Proxy-*），在 start_response 阶段直接 assert 崩 → SSE 接口一律 500，**且发生在调模型之前**——完美解释"一收到命令立刻失败"与"看不到 403"。
- 前端报错来源：`templates/ai_test.html` `aiStreamExecute()` 里 `addChatMessage('执行失败: HTTP ' + response.status)`（fetch `/api/ai/task/execute` 非 200 分支），非 ai_assistant.js:873。

### 已修复（全流程）
1. 新建 `modules/core/wsgi_middleware.py`：`AccessLogMiddleware`（原访问日志功能）+ 包装 start_response **剥除全部 hop-by-hop 响应头**（`filter_hop_by_hop`），waitress/wsgiref 分支通用；app.py `__main__` 改为 import 该模块（原内联类删除）。
2. `templates/ai_test.html`：500 分支改为 `response.text()` 读取响应体、展示真实错误详情（≤300 字符），不再只显示干巴巴的 "HTTP 500"。
3. 实测验证（artifacts/test_hop_by_hop_fix.py）：CASE1 裸应用完整复现线上 AssertionError→500；CASE2 包中间件后 200、Connection 头被剥、X-Accel-Buffering 保留、SSE 分块 0.3s 间隔实时到达（wsgiref 无缓冲流式 OK）。app.py + wsgi_middleware.py 编译通过。

### 遗留（非本次根因，之前排查发现的次要问题）
- hermes_gateway.log 仍有网关重启循环 + 平台↔网关 key 曾漂移（`resolve_hermes_api_server_key()` 自愈合，干净重启对齐）；qwen3.5-omni-plus 曾出现 `Stream stale for 180s`（流式 180s 无 chunk 被杀，omni 系模型偶发，观察即可）。
- 注意区分：网关包 `gateway/platforms/api_server.py` 会把**网关内部**的 agent 异常统一包成 HTTP 500（`Internal server error: {e}`），与本次平台侧 SSE 路由 500 是两回事；前者报错体里已含上游错误详情。
