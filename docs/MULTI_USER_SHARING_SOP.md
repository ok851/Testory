# 多人共享协作 SOP

本文档用于指导团队在当前项目架构下实现“不同账号登录后共享同一业务数据”。  
当前阶段优先基于已有的项目成员机制落地，不依赖新增业务代码。

## 1. 当前基础能力

- 用户体系：users
- 项目隔离：projects
- 项目成员：project_members(project_id, user_id, role)
- 项目权限检查：check_project_access(user_id, project_id, min_role)
- 项目可见性：GET /api/projects 只返回当前用户有权限的项目

可支持共享范围：
- 项目
- 用例与用例目录
- 元素库
- 变量与数据集
- 计划任务
- 执行结果
- 缺陷
- 报告与审计日志

## 2. 推荐角色定义

- admin：平台管理员，管理账号和全局配置
- owner：项目负责人，管理成员与项目设置
- editor：日常执行人员，可编辑内容并触发执行
- viewer：只读人员，查看结果和报告

建议默认分配：
- 测试负责人：owner
- 测试工程师：editor
- 开发/产品/审计：viewer

## 3. 标准操作流程

### 3.1 创建账号
管理员创建账号或开放注册（视部署配置）。

### 3.2 创建项目
由测试负责人或管理员创建目标项目。

### 3.3 把成员加入同一项目
通过现有接口把用户加入项目：
- 查看成员：GET /api/projects/<project_id>/members
- 添加成员：POST /api/projects/<project_id>/members
- 修改角色：PUT /api/projects/<project_id>/members/<user_id>
- 移除成员：DELETE /api/projects/<project_id>/members/<user_id>

### 3.4 成员登录后访问共享数据
成员登录后访问：
- GET /api/projects
即可看到自己有权限的项目，并进入项目使用同一业务数据。

## 4. 多人协作边界与规范

- 不同账号登录后，只要属于同一项目，即可共享该项目内数据。
- 当前共享粒度为“项目级别”，不是“单条用例单独授权”。
- 系统角色 dmin 可查看所有项目；项目内权限仍建议通过项目成员控制。
- 多人同时编辑时，建议先约定分工，避免同一资源反复覆盖。

## 5. 验收清单

### 管理员/owner
- [ ] 能创建账号
- [ ] 能创建项目
- [ ] 能把不同账号加入同一项目
- [ ] 能修改成员角色
- [ ] 能移除成员

### editor
- [ ] 登录后能看到被授权项目
- [ ] 能查看用例、计划、执行结果、缺陷
- [ ] 能在权限范围内编辑和触发执行

### viewer
- [ ] 登录后能看到被授权项目
- [ ] 能查看结果和报告
- [ ] 不能执行高风险写操作

### 跨账号共享
- [ ] A 账号创建项目后，B 账号加入项目可见
- [ ] 不同账号看到的是同一项目数据
- [ ] 移除成员后，对应账号不再可见该项目

## 6. 后续增强建议

1. 增加前端“项目成员管理页”，支持自助邀请
2. 增加邀请链接 / 邀请码 / 邮箱通知
3. 增加团队/分组，支持团队整体加入项目
4. 增加编辑锁或乐观锁，降低并发冲突风险
5. 增加变更通知，提升协作感知

---
当前文档基于现有代码能力整理，适用于“先跑通多人共享、再优化协作体验”的落地路径。

## 6. 当前更新：团队化共享模式

当前版本已弱化传统“用户管理”，改为以团队管理为主入口：

- 顶部菜单进入：`/team-management`
- 管理内容包括：
  - 团队名称
  - 团队码
  - 默认项目绑定
  - 团队成员管理
- 用户流程：
  1. 先自行注册账号
  2. 登录后进入团队管理
  3. 输入团队码加入团队
  4. 自动成为默认项目成员

### 团队码说明
- 团队码仅对当前团队服务有效
- 不同团队服务互不相通
- 不建议启用自动局域网弹窗，需用户手动输入加入

### 管理建议
- 创建团队者为管理员
- 管理员维护团队码与默认项目
- 新成员加入后再由管理员分配团队角色
