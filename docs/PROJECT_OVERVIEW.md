# Testory — AI 多端联动自动化测试平台 项目方案书

---

## 一、项目概述

### 1.1 项目背景与痛点

在企业数字化转型深入推进的今天，大量核心业务流程横跨 **Web 应用、Windows 桌面客户端（ERP/OA/财务系统）、Android 移动端和后端 API** 四大终端。以制造业为例，一条典型的"下单→审批→发货→签收"业务流，往往需要在 Web 端录入订单、在 Windows 桌面 ERP 中审核排产、在 Android 手机端完成现场签收拍照，最后通过 API 校验库存扣减。然而，当前测试工具生态呈现严重的"孤岛化"格局：

- **Web 测试**（Selenium/Playwright/Cypress）仅覆盖浏览器端，无法触达 Windows 原生控件；
- **桌面自动化**（pywinauto/AutoIt）专注于单一桌面应用，缺乏与 Web/Mobile 的协同编排能力；
- **移动端测试**（Appium/UIAutomator）独立运行，无法与 Web/Desktop 流程共享上下文与变量；
- **API 测试**（Postman/JMeter）与 UI 测试完全割裂，断言结果无法跨端传递。

这种割裂导致企业在回归测试阶段面临三大核心痛点：

**痛点一：跨端业务流无法自动化覆盖。** QA 团队不得不手动串联多个单端工具，一条混合流回归耗时 2-4 小时，且高度依赖个人经验，无法纳入 CI/CD 流水线。据行业调研，70% 以上的企业级缺陷发生在跨端交互节点（如 Web 提交后 Desktop 未刷新、移动端状态未同步至后端），而现有工具对此几乎无能为力。

**痛点二：测试结果不可信（"假绿"问题）。** 传统工具在环境缺失、元素定位失败、超时等场景下，往往静默跳过或报告为"成功"，导致 CI 流水线显示绿色而实际存在缺陷。这种"假绿"现象使测试报告丧失门禁价值，开发团队对自动化测试结果的信任度持续下降。

**痛点三：缺乏审计证据链与可追溯性。** 测试执行过程中产生的截图、日志、断言结果散落在不同系统中，无法与运行记录关联。当出现线上事故需要回溯时，团队无法快速定位"哪次测试覆盖了哪个场景、在哪一步产生了什么结果"，合规审计更是无从谈起。

Testory 正是针对上述痛点而生——它不是又一个单端测试工具，而是一个**以"执行诚实"为第一原则的多端联动质量保障平台**。

### 1.2 目标用户画像

| 用户角色 | 典型特征 | 使用场景 | 核心诉求 |
|----------|----------|----------|----------|
| **QA 测试工程师** | 2-5 年经验，熟悉 Web/接口测试，正在学习自动化 | 编写和执行跨端用例、查看测试报告、定位失败原因 | 降低跨端测试编写门槛；失败步骤有截图和日志可追溯 |
| **测试负责人 / 测试经理** | 管理 5-20 人 QA 团队，负责质量门禁 | 配置 CI/CD 集成、审批高风险操作、导出审计报告 | 测试结果可信可门禁；跨端覆盖率可量化；审计包一键导出 |
| **DevOps 工程师** | 维护 Jenkins/GitLab CI 流水线 | 将测试接入流水线、配置自动触发和回调 | 机器可读的测试结果（JUnit/XML）；CI 红绿灯准确映射执行结论 |
| **企业 IT 管理员** | 负责内部系统运维，管理 Windows ERP/OA 客户端 | 部署私有化实例、配置 SSO/LDAP、管理用户权限 | 数据不出内网；支持企业级认证和审计日志 |
| **独立开发者 / 小团队** | 1-3 人团队，快速迭代产品 | 用自然语言描述测试场景，AI 自动生成用例并执行 | 零配置上手；AI 辅助降低编写成本；桌面端也能自动化 |

### 1.3 项目核心价值主张

Testory 通过**多 Agent 协同编排引擎 + 四端统一执行面 + 执行诚实门禁体系（S1-S4）**，解决企业级跨端业务流无法自动化覆盖、测试结果不可信、缺乏审计证据链三大核心痛点，为 QA 团队和 DevOps 工程师带来**一次触发→多端协同→诚实验证→可审计沉淀**的全链路质量保障能力。

## 二、技术方案与路线

### 2.1 智能体设计

Testory 采用**多角色 Agent 协同架构**，将测试全流程拆解为五个核心角色，各司其职、通过共享状态协调推进：

#### 2.1.1 角色定义

| 角色 | 职责 | 核心能力 |
|------|------|----------|
| **Planner（规划师）** | 接收自然语言描述或结构化需求，分解为跨端执行计划（CrossEndPlan） | NL→Plan 分解、多端任务图生成、阶段依赖推导 |
| **RiskAdvisor（风控顾问）** | 评估每个执行阶段的风险等级（L0/L1/L2），决定是否需要人工审批 | 风险分级、审批令牌管理、L2 门禁阻断 |
| **WebApiExecutor（Web/API 执行器）** | 执行 Web 浏览器操作和 API 调用 | Playwright 驱动、CDP 协议、API 断言引擎 |
| **DesktopExecutor（桌面执行器）** | 执行 Windows 原生桌面应用操作 | pywinauto/UIA 控件操作、零配置窗口发现、截屏验证 |
| **Verifier（验证官）** | 汇总各端执行结果，进行跨端一致性验证，生成最终报告 | 多端状态比对、断言聚合、证据包打包 |

#### 2.1.2 核心工作流

`
用户输入（自然语言 / 结构化 Plan）
        │
        ▼
   ┌─────────┐     ┌───────────┐
   │ Planner │────►│RiskAdvisor│
   └────┬────┘     └─────┬─────┘
        │                │ L2审批？
        ▼                ▼
   ┌─────────────────────────────┐
   │     CrossEndPlan (阶段图)     │
   │  Stage1(Web) → Stage2(Desktop)│
   │       → Stage3(Mobile/API)   │
   └──────────────┬──────────────┘
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │WebExec │ │DeskExec│ │APIExec │
   └───┬────┘ └───┬────┘ └───┬────┘
       │          │          │
       └──────────┼──────────┘
                  ▼
           ┌──────────┐
           │ Verifier │
           └────┬─────┘
                ▼
         证据包 + 报告
`

#### 2.1.3 提示词策略

- **分层提示词架构**：系统级提示词定义角色约束（如 Planner 只产出 Plan、Verifier 只做判定不做执行）；任务级提示词注入当前上下文（跨端变量、历史失败模式）；
- **工具调用绑定**：每个 Agent 绑定专属工具集（Web→Playwright CDP、Desktop→UIA/ScreenCapture、API→HTTP Client），通过 Function Calling 协议调用；
- **失败记忆注入**：从 IncidentMemory 中检索同类历史失败的 Runbook，注入 Planner 和 Verifier 提示词，避免重复犯错。

#### 2.1.4 知识库构建

| 知识来源 | 用途 | 更新机制 |
|----------|------|----------|
| **IncidentMemory** | 存储历史失败案例、根因分析、修复方案 | 每次运行后自动入库（失败自动写入，成功需审批） |
| **Runbook 库** | 标准化故障处理流程 | 从成功运行中自动沉淀 Skill 草稿 |
| **Element Locator Cache** | 元素定位器历史快照与恢复策略 | AI 选择器恢复引擎自动维护 |
| **Scenario Templates** | 预置跨端场景模板（下单、审批、签收等） | 由 Planner 在分解时自动匹配 |

#### 2.1.5 插件/工具调用逻辑

Agent 通过 **MCP（Model Context Protocol）工具连接层** 与真实环境交互：

| 工具类型 | 实现方式 | 调用场景 |
|----------|----------|----------|
| Web 操作 | Playwright CDP + 浏览器扩展注入 | 页面导航、元素交互、截屏 |
| 桌面操作 | pywinauto UIA + ScreenCapture | 控件点击、窗口发现、OCR 提取 |
| 移动操作 | ADB + Appium + 设备推送 | 安装 APK、点击滑动、截图 |
| API 调用 | HTTP Client + 断言引擎 | 接口请求、响应校验、变量提取 |
| 视觉感知 | OpenCV + 本地 VLM（LLaVA） | 元素视觉定位、截图比对、验证码识别 |

### 2.3 技术可行性分析

#### 2.3.1 技术选型与路线

| 层级 | 技术选型 | 选型理由 |
|------|----------|----------|
| **Web 后端** | Flask + APScheduler | 轻量成熟、社区生态丰富、便于私有化部署 |
| **Web 前端** | Tailwind CSS + Jinja2 模板 | 零构建依赖、服务端渲染、桌面客户端复用 |
| **桌面客户端** | pywebview + Tauri（可选） | 本地 WebView2 渲染，无需 Electron 体积 |
| **Web 自动化** | Playwright | 原生 CDP 支持、多浏览器兼容、稳定可靠 |
| **桌面自动化** | pywinauto (UIA/Win32) | Windows 原生控件识别、零额外依赖 |
| **移动端自动化** | ADB + Appium | Android 标准协议、模拟器/真机通用 |
| **AI 推理** | 多 LLM Provider 适配 | 支持 OpenAI/Azure/DeepSeek/通义千问/Ollama 等 10+ 供应商 |
| **视觉 AI** | OpenCV + 本地 VLM | 元素视觉定位、验证码识别，无需云端依赖 |
| **数据存储** | SQLite + JSON 文件 | 零配置、单文件部署、满足中小团队需求 |

#### 2.3.2 关键难点与解决方案

| 难点 | 解决方案 |
|------|----------|
| **跨端变量透传** | 设计 CrossEndContext 共享状态总线，每个阶段的输出变量自动注入下一阶段的输入上下文，支持字符串/JSON/文件三种透传模式 |
| **Windows 桌面控件识别不稳定** | 多级定位策略：UIA AutomationId > Name > Class > 坐标；结合 AI 视觉定位作为兜底；零配置"选择当前窗口"降低配置门槛 |
| **执行结果"假绿"** | S1-S4 执行诚实标准：默认失败、显式成功；环境缺失→失败而非跳过；warning 不得映射为 CI 绿灯 |
| **多 LLM 兼容性** | 统一 Provider 适配层（ai_multi_provider.py），屏蔽 OpenAI/Azure/Ollama 等接口差异；支持本地推理降级 |
| **长时间任务的人工介入** | HITL（Human-in-the-Loop）机制：高风险操作暂停等待人工确认/取消，超时自动失败 |

#### 2.3.3 与现有方案的对比优势

| 维度 | 传统方案（Selenium+Appium+pywinauto） | Testory |
|------|---------------------------------------|---------|
| 跨端编排 | 需手动串联脚本，无共享状态 | 原生跨端 Plan + 变量透传 + 同步点 |
| 执行可信度 | 各工具各自报告，无统一门禁 | S1-S4 标准，CI 红绿灯准确映射 |
| 桌面支持 | 需手动配置控件路径 | 零配置窗口发现 + AI 视觉兜底 |
| AI 辅助 | 无 | NL→Plan、智能定位器恢复、视觉感知 |
| 审计能力 | 无 | 证据包（Trace ZIP）、HITL/Risk 事件、客户审计包 |
| 部署方式 | 多工具分别部署 | 单一平台、单 exe 安装包 |

## 三、业务价值验证

### 3.1 痛点解决路径

| 痛点 | Testory 解决路径 | 关键机制 |
|------|-----------------|----------|
| **跨端业务流无法自动化** | Planner Agent 将自然语言分解为 CrossEndPlan → 多端 Executor 协同执行 → 变量自动透传 | CrossEndContext 状态总线 + 阶段同步点 + 恢复引擎 |

| **跨端缺陷难复现** | 运行历史完整记录每步操作、截图、变量 → 同环境可稳定复现 | run_history + step_results + S3 可追溯标准 |

## 四、创新点与差异点

### 4.1 技术创新

**1. 执行诚实门禁体系（S1-S4）**
业界首创将"不假绿"作为平台级第一原则。通过四条硬标准（不假绿、不假传、可复现可追溯、流水线可接入），从架构层面杜绝测试结果美化。所有执行通道（单用例、批量、调度、跨端、AI 任务）统一服从门禁映射：只有 success 一种状态算通过，warning/skipped 在 CI 中一律判红。

**2. 多角色 Agent 协同编排**
不同于传统"单 Agent 做所有事"的模式，Testory 将测试流程拆解为 Planner→RiskAdvisor→Executors→Verifier 五个专业角色，通过共享 TestRunState 协调推进。每个角色有独立的工具集和决策边界，支持 HITL（人工介入）和 L2 风险审批门禁。

**3. AI 多级定位器恢复引擎**
当标准定位器（ID/XPath/CSS）失效时，自动启用四级恢复策略：AI 语义匹配→视觉定位（OpenCV/VLM）→相似元素推断→截图人工确认。结合 Element Locator Cache 和选择器历史快照，显著提升脚本在 UI 变更下的存活率。

**4. 多 LLM Provider 统一适配层**
支持 10+ 大模型供应商（OpenAI/Azure/DeepSeek/通义千问/Ollama/智谱等）的无缝切换，统一 Function Calling 协议，支持本地推理降级。企业可根据数据合规要求选择云端或本地部署的模型。

### 4.2 场景创新

**1. 首创"Windows 桌面 + Web + Mobile + API"四端联动测试**
填补了业界在 Windows 原生桌面应用（ERP/OA/财务系统）与 Web/Mobile 混合流自动化测试的空白。零配置窗口发现 + AI 视觉兜底，使桌面端自动化门槛大幅降低。

**2. 跨端变量透传与状态同步**
一条业务流的 Web 端订单号可自动透传至 Desktop 端 ERP 审核、Mobile 端签收、API 端库存校验，全流程变量一致、状态可追溯。这在传统方案中需要手动维护共享文件或数据库。

**3. 人机协同（HITL）+ 风险分级审批**
高风险操作（如删除数据、生产环境执行）自动暂停等待人工确认；L2 级操作需要审批令牌才能继续。这使自动化测试可以安全地应用于准生产环境。

**4. 证据链驱动的审计合规**
每次运行自动生成 Trace ZIP 证据包（含步骤结果、截图、HITL/Risk 事件、CI 链接），支持一键导出客户审计包。满足金融、政务等行业的合规审计要求。

### 4.3 差异化竞争力

| 竞品类型 | 竞品代表 | Testory 差异化壁垒 |
|----------|----------|-------------------|
| **视觉 AI SDK** | Midscene.js | Testory 是完整测试平台（用例管理/历史/报告/CI），非仅 SDK；且深度支持 Windows 桌面 |
| **Web 测试 SaaS** | Testim / Mabl | Testory 支持 Windows 原生客户端 + 本地/私有化部署；SaaS 无法触达企业内网桌面应用 |
| **移动端测试平台** | Appium Cloud / Sauce Labs | Testory 将 Mobile 作为四端之一纳入统一编排，而非孤立的移动端测试 |
| **裸自动化框架** | Playwright / Appium 原生 | Testory 提供 NL→Plan→执行→证据→CI 的完整产品层，而非仅脚本框架 |
| **国内测试平台** | MeterSphere / 飞测 | Testory 以 Windows 桌面混合流为独特切入点，且拥有执行诚实门禁体系 |

**核心壁垒总结：**
1. **Windows 桌面深度**：零配置窗口发现 + UIA 控件操作 + AI 视觉兜底，这是纯 Web/SaaS 方案无法企及的；
2. **执行诚实第一原则**：S1-S4 标准从架构层面杜绝假绿，使 CI 门禁真正可信；
3. **开源飞轮**：核心执行引擎 Apache-2.0 开源，企业增强（SSO/审计/并行农场）可选交付，不锁定用户；
4. **证据链治理**：Trace ZIP + 客户审计包 + HITL/Risk 事件链，满足高合规行业的审计刚需。
